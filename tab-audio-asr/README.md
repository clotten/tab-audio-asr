# 网页视频转文字（Edge / Chrome 插件）

把正在播放的网页视频/直播/网课的声音抓下来，实时切成句子送识别，**视频页浮窗文字稿**边播边累积，最后导出 TXT / SRT。

已用真实 key 跑通：`Qwen/Qwen3-ASR-1.7B` 对插件自己编码的 16k 单声道 WAV 识别正常（见「实测数据」）。

---

## 一、核心问题：网页视频的音频到底怎么拿？

浏览器里的"视频"有四种完全不同的存在方式，对应四条技术路线。**选错路线会卡死**，这是项目最关键的设计判断。

| 方案 | 原理 | 覆盖面 | 代价 |
|---|---|---|---|
| **A. 标签页音频捕获**（本插件） | `chrome.tabCapture.getMediaStreamId()` 把标签页的**声音输出**重定向给扩展，`getUserMedia` 拿到 MediaStream | B 站、YouTube、网课、直播、播客**全部通吃**。不管视频是 `<video src>`、`blob:`、MSE 拼接还是 HLS/DASH 分片，甚至 DRM 加密的片子，进入扬声器的那路声音都能拿到 | 必须用户点一下开始；捕获期间原标签页声音被扩展接管，需要自己回放（或故意不回放做"静音录制"） |
| B. 抓媒体文件 URL 再下载 | 拦截 `.mp4/.m4a/.ts` 请求，或读 `<video>.currentSrc` | 只在"直链媒体"站点有效（播客、直接上传的视频） | `blob:` 根本没有 URL；HLS 要拼几百个分片；防盗链与 DRM 全挡 |
| C. 页面内 Web Audio 抓取 | content script 里 `createMediaElementSource(video)` | 精确、不需回放 | **跨域视频踩 CORS**：视频没带 CORS 头时输出的就是静音，且一旦创建无法重建。B 站/YouTube 全中招 |
| D. `getDisplayMedia` 共享标签页 | 用户手动选"共享此标签页并共享音频" | 全场景覆盖 | 每次弹选择框，交互最重 |

**结论：做通用插件只有 A 能落地。** 你要的不是"视频文件"，而是"这段视频正在发出的声音"——直接在扬声器前截流，绕过所有容器格式、防盗链和 DRM 问题。

### 数据流

```
用户点开始
   │
   ▼
popup ──START──▶ Service Worker ──chrome.tabCapture.getMediaStreamId(tabId)──▶ streamId
   │                  │
   │                  ├── ensureOffscreen() ──▶ offscreen.html/js（长期存活）
   │                  └── injectSubtitle() ──▶ content/subtitle.js（视频页浮窗文字稿）
   │                                                  │
   │                                        getUserMedia({audio:{chromeMediaSource:'tab', id}})
   │                                    ┌─────────────┴──────────────┐
   │                                    ▼                            ▼
   │                          回放到扬声器（静音录制则不回放）   AudioWorklet 直取 16k PCM
   │                                                              │  （实时通路）
   │                                                              ▼
   │                                     流式切句：停顿 600ms 就切一句
   │                                                              │  每句一个 16bit WAV，立刻上传
   │                                                              ▼
   │                                    POST /v1/audio/transcriptions（串行队列+重试）
   │                                                              │  每句带 startMs / durationMs
   │                                        ┌───────── STATE_SET 消息 ─────────┐
   │                                        ▼                                  │
   └──────────────── offscreen（内存状态）──▶ Service Worker ──▶ chrome.storage.local
                                                                      │
                                                ┌────────────────────┴──────────────┐
                                                ▼                                   ▼
                                         popup 实时渲染                   浮窗文字稿（按时间轴高亮）
```

四个关键工程细节，全是踩坑点：

1. **offscreen 文档里只有 `chrome.runtime`，没有 `chrome.storage`**。Chrome 官方文档原话：为了降低扩展把这些 API 当作"后台页面替代品"的可能，**仅向屏幕外文档公开 Messaging API**。所以状态留在 offscreen 内存里，落盘一律通过消息交给 Service Worker。写成 `chrome.storage.local` 不会在加载时报错，而是等你点了「开始转录」才抛 `Cannot read properties of undefined (reading 'local')`——第一版就栽在这，现在有 `tools/lint-offscreen-apis.mjs` 静态拦。
2. **为什么必须用 offscreen 文档**：MV3 的 Service Worker 里没有 `MediaRecorder`、没有 `AudioContext`，而且空闲 30 秒就被杀。录音必须放 offscreen。好处是**关掉弹窗、SW 被回收，录音都不会中断**。
3. **为什么不给 MediaRecorder 设 `timeslice`**：设了以后只有第一块带 WebM 头，后面的块单独 `decodeAudioData` 会直接抛错。所以每段都是"新建 recorder → 录满 N 秒 → stop"，保证每块完整可解码。
4. **为什么 WAV 要 16k 单声道**：语音模型输入本来就是 16k 单声道，1 分钟只有 1.9 MB，同时彻底绕开"接口认不认 webm/opus"的不确定性。已实测该格式被接口接受。

## 二、"能不能一开始就把整体音频拿去转，而不是跟着播放慢慢出字？"

**分两种情况。**

### ① tabCapture 模式下：不能，这是物理限制

tabCapture 截的是**播放时的声音输出**。视频没播到第 10 分钟，那分钟的声音在任何你能访问的地方都不存在——没文件、没缓冲、没 API。

而且**瓶颈根本不在模型**。实测：15.2 秒音频识别耗时 0.9 秒，即 **16.9 倍实时**。"出字慢"不是模型慢，是音频还没产生。

### ② 直链媒体（播客 / 直接上传的视频 / `.mp3`、`.m4a` 直链）：可以

`<video>.currentSrc` 是真链接时，扩展能 `fetch` 整个文件，本地解码后一次/几次提交，**20 分钟音频约 1 分钟转完**。但 B 站/YouTube 是 `blob:` + MSE 分片，链接在内存里，走不通。这条"整段模式"还没做，需要的话可以加。

### ③ 三个立刻可用的提速手段

| 手段 | 效果 | 代价 |
|---|---|---|
| 每块秒数调到 10–20 秒（默认 20） | 更早开始送识别 | 请求变多 |
| **视频调到 1.5–2 倍速播放** | 总时长直接砍半 | 实测准确率几乎不掉 |
| 先播再点开始 | 避免开头几句被截断 | — |

倍速实测（同一段 112 字文本，TTS 按不同语速合成后识别）：

```
语速   音频时长   识别耗时   相似度
1.00x   15.2s      900ms    93.1%
1.25x   12.4s      869ms    91.7%
1.50x   11.5s     1165ms    91.7%
2.00x    8.9s      790ms    93.1%
```

相似度差异在 1.5 个百分点内、基本是噪声，**2 倍速完全可用**。

## 三、安装（Edge）

1. 打开 `edge://extensions/`，左下角打开「开发人员模式」。
2. 点「加载解压缩的扩展」，选择本目录 `tab-audio-asr`（包含 `manifest.json` 的那一层）。
3. 点插件图标 → 展开「设置」→ 填 **API Key** → 点「自测接口」。返回 200 说明 key、模型名、网络全通。
4. 打开有声音的网页并播放 → 点插件图标 → 「开始转录」。

> 改完任何文件都要在 `edge://extensions/` 里点一下插件的**刷新**按钮；改了 Service Worker 或 manifest 之后尤其必须刷新。

## 四、视频页浮窗文字稿

点开始后会在视频页注入一个浮窗，把识别结果按行累积显示（不是单行字幕）：

- 顶部：红点 + 计时 + 模型名 + 关闭按钮（关闭等于把开关关掉，可在插件里重开）
- 正文：每行 `时间戳 + 一句文本`，**跟着视频进度自动高亮当前这一句**
- 最后一行可能是**灰色斜体的临时预览**（这一句还没说完，`…` 结尾），说完后会被定稿替换
- 自动滚到最新；**你手动往上翻就停止自动滚动**，右侧出现「回到最新」按钮
- **可拖动**（按住顶部条拖）位置记进设置；**右下角可拉大小**，尺寸也记进设置
- 停止 15 秒后自动淡出
- 页面跳转/刷新会自动重新注入；视频全屏时会把节点搬进全屏容器

已知限制：**如果播放器是把 `<video>` 元素本身全屏**（而不是包一层 div），浏览器不允许在 `video` 内部叠 DOM，浮窗会看不见（YouTube/B 站是容器全屏，不受影响）。这种情况会尝试把父容器顶成全屏，失败就算了。

### 整段预扫（想更快拿到整篇稿子）

弹窗里的「整段预扫」会让页面里的视频**跳回开头、静音、按倍速播放一遍**，专门用来生成整段字幕稿：

- 因为开了「静音录制」，你听不到声音，但音频照样进识别管线
- 播完（`ended` 事件）自动停止录制
- 倍速可设 1–2 倍，默认 **1.5 倍**（实测 1.5x 准确率最好，2x 开始掉，4x 直接崩）
- 注意：这**不是"偷偷提前"**——画面是真的在快进，只是靠插件不出声；所以字幕时间戳仍然对得上

实测倍速对准确率的影响（同一句话）：

| 语速 | 1.0x | 1.5x | 2.0x | 2.5x | 3.0x | 4.0x |
|---|---|---|---|---|---|---|
| 相似度 | 64% | **90%** | 71% | 61% | 58% | 35% |

所以「8 分 48 秒的网课，1.5 倍预扫约 6 分钟出全稿」是可靠的；4 倍速已经不能用了。

### 同时保存音频（WAV）

勾上「同时保存音频」，录制期间会把原始音频写成 WAV 文件，录完点「保存音频」直接下载。

- 格式：16k / 16bit / 单声道 WAV（和送识别的一模一样，约 1.9 MB/分钟，1 小时约 115 MB）
- 实现：走 **OPFS**（浏览器私有文件系统）边录边写，**不占内存**——攒在内存里 1 小时会吃掉 115MB，容易把后台页面拖崩
- WAV 头先写 44 字节占位，停止时 `seek(0)` 回填真实长度
- popup 和 offscreen 同源共享 OPFS，所以下载不用经过消息传几 MB 数据
- 大小 / 时长会记在会话里，弹窗进度栏能看到

拿到 WAV 之后，既可以重新喂给识别接口跑更长的上下文，也可以拿去做别的处理。

### 离线精校（质量最强的一档）

录完点「离线精校」：用保存的 WAV **按 20 秒上下文**重新识别一遍，再自动跑一次整段纠错，然后整体替换实时结果。

为什么值得——同一段 8.9 分钟网课（插件自己录的 WAV）实测：

| 指标 | 插件实时（1–6 秒切句） | 离线精校（20 秒上下文） |
|---|---|---|
| 句数 / 字数 | 146 / 1397 | **80 / 1883** |
| `帧`（正确） | 12 | **51** |
| `针/真/贞`（错） | 24 | **3** |
| `MAC`（正确） | 10 | **23** |
| `MAX/back`（错） | 2 | **0** |
| `手部`（错） | 3 | **0** |

开头对比更直观：

```
实时：  I'm a little bit of a dreamer. / 今天我们学习五。 / 烂。 / 局网的组成。
离线：  同学们好，我是郑红老师。今天我们学习无线局域网 WLAN。
        本部分包括以下四个内容：无线局域网的组成、802.11 局域网的物理层。
        802.11 局域网的 MAC 层协议和 802.11 局域网的 MAC 帧。
```

实现要点：

- 从 OPFS 读 WAV，按 **3 分钟窗口**切片处理（1 小时音频解码后 230MB，不能一次读进内存）
- 每窗口内用批量 VAD（`maxRegionMs: 20000`）切句，逐句上传
- 跑完自动接一次「校正全文」
- 8.9 分钟音频约 **50 秒**跑完（比实时从头播一遍快 10 倍）

同样的能力也有命令行版：`tools/transcribe-file.mjs`，可以转任意音频文件并和参考 SRT 对比。

### 「校正全文」和「离线精校」有什么不一样

| | 校正全文 | 离线精校 |
|---|---|---|
| 输入 | 已有的**文字** | 保存的**音频** |
| 做什么 | 用术语表 + 上下文改同音错字，不增删行 | 重新切句（20 秒上下文）→ 重新识别 → 再纠错 |
| 能救回漏掉的内容吗 | **不能**。实时版把 "今天我们学习 802.11 无线局域网的组成" 切成了 `今天我们学习五。` / `烂。` / `局网的组成。`，字已经被切没了 | **能**。长上下文重跑后是完整的一句 |
| 耗时 | 每 40 句约 3 秒 | 8.9 分钟音频约 50 秒 |
| 前提 | 有 API Key | 录制时勾了「同时保存音频」 |

所以：**能重跑就重跑**，校正只是没存音频时的补救。弹窗在停止后会直接提示你点精校。

### 延迟是怎么降下来的

tabCapture 有物理下限：**音频必须先被播放出来才能被识别**。但"等 20 秒"完全是可以避免的工程问题，之前慢的真正原因是：

> 老实现是"录满 20 秒 → 解码 → 切句 → 上传"，一句在块开头说完，要等整块录完才发出去，**最坏等 19 秒**。

现在换成**实时通路**：`AudioWorklet` 直接拿 16k PCM → 流式切句 → 停顿 600ms 就认为一句说完 → 立刻编码上传。延迟变成：

| 环节 | 耗时 |
|---|---|
| 等停顿（判断一句话说完） | 0.6 秒 |
| 切点容差 + 编码 WAV | < 0.05 秒 |
| 上传 + 识别（15 秒音频约 0.9 秒，3 秒音频约 0.5 秒） | 0.3–1.0 秒 |
| **一句说完 → 浮窗出现文字** | **约 1–2 秒** |

连续讲话（一直不停顿）时会在 5 秒处找能量最低点切开，延迟上限约 6 秒；硬上限 10 秒兜底。这些都有离线测试（`tools/test-stream.mjs` 直接测"说完到吐出"的毫秒差）。

### 增量提交：说完一句就出字，不等整段

借鉴 LiveTranslate 的 `_do_interim_asr`。它比"做个预览"高明的地方在于：**识别结果是可以直接用的**。

说话过程中（每 ≥2 秒、且这段已积累 ≥1.8 秒），把正在增长的缓冲送去识别一次，然后：

1. 按**文本标点**切句（不是按音频能量），**最后一句**还在说，其余都已完整；
2. 完整的句子**立刻提交**进正文；
3. 按"已提交字数占比"把这段音频从缓冲头部**裁掉**（+0.3 秒余量防回声，至少留 0.5 秒）；
4. 记住已提交文本的**尾巴**（50 字），下一轮新结果开头如果是它的后缀，就掐掉——这就是回声去重；
5. ≤3 汉字 / ≤8 字母的碎片不单独成行，攒到下一句前面；
6. 最后那句显示成灰色斜体"正在说…"，等这句真的说完，由定稿覆盖。

**为什么切点要用文本决定**：这是我在实时回放里发现的真问题。用能量谷切音频时，`本部分包括以下四个内容` 被切成 `本部。`；而按标点切，句子永远不会从中间断。

代码：纯逻辑在 `lib/incremental.js`（39 条离线断言），接线在 `offscreen.js` 的 `maybeInterim()`，裁音频靠 `lib/vad.js` 的 `trimFront()`。

> 实测提醒：这套机制对**连续说话**有效；如果说话人每 2–4 秒就停顿，缓冲里永远只有一句，增量的提交次数会是 0——那时起作用的是"正在说"那行预览（同一次请求里顺带得到，不额外花钱）。79 秒样本就是这种情况，见下文实测。

开关在设置里叫「增量提交」，关掉就退回纯定稿模式。

如果页面环境不支持 AudioWorklet 或被自动播放策略挂起，会自动退回旧的 MediaRecorder 分段通路（弹窗里会显示"分段通路"），功能不受影响，只是慢。

## 五、静音播放怎么办

如果页面本身静音（`<video muted>`、播放器音量 0、标签页被静音），捕获到的就是静音——这是必然的。

正确做法是用 **「静音录制（捕获声音但不放出来）」** 开关：

- tabCapture 会把标签页声音从扬声器"借走"，不回放就等于**你自己听不到，但音频照样进识别管线**
- 适合深夜看网课、不想外放、或者本来就不想听声音的场景
- 注意：**不要用播放器自带的静音按钮**，那会让音频源直接变成静音；要用本插件的开关

## 七、切句策略（决定字幕质量的地方）

识别接口不返回时间戳，所以时间轴只能靠本地切：`lib/vad.js` 用能量法在静音处断开。

但**切太细会毁掉准确率**——实测把课堂录音切成 1–2 秒的碎片时，`RTS帧` 会被识别成 `RTS针`、`CTS帧` 变成 `CT、X光`，因为模型失去了上下文。所以两条通路都做了"碎句合并 / 最低长度"约束：

**批量通路**（MediaRecorder 回退时用）：

| 参数 | 默认 | 作用 |
|---|---|---|
| `minGapMs` | 600ms | 短于这个的气口不算句间停顿 |
| `targetMinMs` | 2500ms | 太短的段会跟邻居合并，保证每句有足够上下文 |
| `maxJoinGapMs` | 1500ms | 合并时允许跨越的最大间隙 |
| `maxRegionMs` | 10000ms | 单句上限，超了在能量最低处强行切开 |

**实时通路**（AudioWorklet，默认）：

| 参数 | 默认 | 作用 |
|---|---|---|
| `silenceGapMs` | 600ms | 停顿这么久就切，这是延迟的主要来源 |
| `targetMinMs` | **2000ms** | 不足这么长先不切，等下一句合并。实测：800ms 时 **30%** 的段是 2 秒内碎片（就是 `本部。`/`魏征。` 那种）；2000ms 时**碎片为 0**，平均 3.7 秒 |
| `graceSilenceMs` | 1200ms | 短句后静音超过 1.2 秒还没人接话，就别等了 |
| `softCutMs` | 5000ms | 连续讲话时在能量最低处切 |
| `hardCutMs` | 10000ms | 硬上限兜底 |

最终每句大约 **2–6 秒**：太短的会合并，长句会被切开，既够上下文，又能让浮窗两三秒增加一行。

### 术语/专有名词听错，是模型的问题吗？

**不是模型能力问题，是被切句打断了上下文。** 实测（同一段 TTS 音频，4 个模型）：

| 音频 | Qwen3-ASR-1.7B | XingChenASR-V3.2-Ultra | XingChenASR-V3.2 | SenseVoice |
|---|---|---|---|---|
| 12 秒（三句连读） | 802.11✓ MAC✓ 局域网✓ | 全部✓ | 全部✓ | 全部✓ |
| 5 秒（只切出目标句） | 802.11✗ 局域网✗ | 802.11✗ | 802.11✗ | 802.11✗ |

同一段内容，切短以后**四个模型全错**（`802.11` 变成 `20的2班斯滩`、`二十的二班是摊`），给足上下文又全部正确。所以换模型不会解决，加长上下文/事后纠错才会。

另外实测：硅基流动的识别接口会**接受但忽略** `prompt` / `hotwords` / `language` / `context` 四个字段（都返回 200，结果与不带完全一致）——所以在识别阶段做术语偏置这条路是堵死的。

### 补救措施（通用机制 + 你自己的领域数据）

这里有条重要的设计红线：**插件里不内置任何具体课程的术语**。术语是领域数据，写死在默认值里就是把特例当功能——换个科目全废，还可能误伤正常文本。

所以分成"通用机制"和"你的数据"两部分：

**通用机制（不需要任何配置）**

1. **校正全文**：把整段稿子（连同上下文）交给对话模型改同音错字，不乱增删行。它不需要预先知道"错法"，靠上下文判断。
2. **术语表提示**：你在设置里填的术语，会作为"这些词必须这样写"的约束一起交给模型。
3. **本地即时替换**：只有你写了 `错 => 对` 的行才做字符串替换（错法确定时才用），零延迟。

**你的数据（默认是空的）**

默认术语表为空。要用请自己填，或者从 `examples/` 里复制一份改成自己的：

```
examples/glossary-计算机网络.txt    ← 802.11 / MAC 帧 那一套（本课程用）
```

同一段真实录音（79 秒）实时回放，两种配置的差别：

| 配置 | 字数 | `帧`(对) | `针/真/贞`(错) | `MAC`(对) |
|---|---|---|---|---|
| 零术语（纯通用机制） | 148 | 0 | 6 | 1 |
| 填了 examples 里的术语表 | 155 | 3 | 3 | 2 |

也就是说：**通用机制负责"不改坏、能纠错"，术语表负责"这门课的行话"**。后者一定要你自己给（或从示例改），插件不该猜。

纠错模型实测对比（同一份 7 行稿子）：

| 模型 | 耗时 | 效果 |
|---|---|---|
| `Qwen/Qwen2.5-7B-Instruct`（默认） | 2.7s | 最好：修掉 4 处，无编造 |
| `THUDM/GLM-4-9B-0414` | 2.5s | 修掉 2 处 |
| `Qwen/Qwen3-30B-A3B-Instruct-2507` | 3.2s | 编造了"MAC 局域网"（不推荐） |
| `Qwen/Qwen3-8B` | 40s | 太慢（思考型） |

每 40 句一批，所以一小时视频大约 10 次请求。

### 片头音乐会被编成假句子（已修，两层防护）

插件自己产出的第一版 SRT 里有这么两句：

```
00:00:00  中国共产党中央委员会。            ← 0.92 秒，11 个字
00:00:04  I'm a man of few words.          ← 片头音乐
00:00:09  I'm a stranger in a strange land.
```

`I'm a man of few words` / `I'm a stranger in a strange land` 是 Whisper 系模型在**静音/纯音乐**上的标志性幻觉——模型面对"听不清但必须输出点什么"的输入，会吐出训练数据里的高频字幕句子。根因是能量 VAD 只看响度，片头音乐能量够大就被当成语音送进去了。

**第一层：Silero VAD（真正的语音/非语音分类）**

浏览器内跑 [Silero VAD](https://github.com/snakers4/silero-vad)（ONNX，`onnxruntime-web` wasm 单线程）。在你的真实录音上实测：

| 区间 | 平均语音概率 | >0.5 的帧占比 |
|---|---|---|
| 片头静音（0–4s） | 0.005 | 0% |
| **片头音乐（4–24s）** | **0.003** | **0%** |
| 音乐结束静音（24–26s） | 0.000 | 0% |
| 老师开场白（26–60s） | 0.625 | 63% |
| 讲课中段（60–300s） | 0.538 | 53% |

音乐段均值 0.003、讲话段 0.5+，界限干净得离谱。所以现在的判定很简单：**一段音频的平均语音概率 < 0.25 → 直接丢，连识别请求都不发**（省时间也省钱）。

实现细节：

- 模型 `silero_vad_v5.onnx`（2.2MB）+ `ort.wasm.min.js`（49KB）+ `ort-wasm-simd-threaded.mjs`（24KB 加载器）+ `ort-wasm-simd-threaded.wasm`（13.6MB）都在 `vendor/` 里，**不需要用户装任何环境**
- ⚠️ **`.mjs` 和 `.wasm` 缺一不可**。ORT 1.30 的 wasm 后端先 `import()` 那个 `.mjs` 加载器，再由它去取 `.wasm`。第一次打包漏了 `.mjs`，浏览器就报 `no available backend found ... Failed to fetch dynamically imported module`——现在有 `tools/check-vendor.mjs` 静态拦（会顺着 bundle 里引用的文件名逐个核对，并检查 CSP 有没有 `wasm-unsafe-eval`）
- 弹窗设置里有 **「VAD 自检」** 按钮：依次走"运行时 → 取模型 → 建会话 → 跑一帧推理"，失败时直接告诉你卡在哪一步、原因是什么，不用猜
- MV3 禁止远程加载代码，所以 wasm 必须打包；manifest 里加了 `script-src 'self' 'wasm-unsafe-eval'`
- `ort.env.wasm.numThreads = 1`（没有 COOP/COEP，不能用 SharedArrayBuffer）
- Silero 是 512 采样（32ms）一帧的 RNN，必须逐帧顺序喂、回传 state；推理是异步的，所以用 Promise 链串起来并按帧号存概率
- **加载不阻塞录制**：15.9MB 的 wasm 首次编译可能好几秒，所以是后台加载 + 把这段时间的 PCM 缓存下来、就绪后回填（片头音乐正好在这段里，不能让 VAD 错过它）。早期版本把它写在阻塞路径上，8 秒超时导致直接回退——已修
- 加载失败不影响使用：`diag.vadError` 记的是**真实原因**（哪一步失败），弹窗显示"能量 VAD"

**第二层：结果侧的通用约束（没有句子黑名单）**

`lib/hallucination.js` 只保留**与内容无关**的物理约束，三条都不依赖任何具体词：

1. **语速上限**：字数 ÷ 时长 > 11 字/秒 → 物理上不可能是这段音频的内容（上例 0.92 秒 11 个字正好被这条逮住）；
2. **稀疏下限**：时长 ≥ 8 秒且字/秒 < 0.8 → 那是音乐/噪声里的杂音（真实案例：18.4 秒的片头音乐被识别成 `Oh, oh`，0.27 字/秒）；
3. **复读检测**：同一段 3–20 字的片段重复 ≥3 次 → 自回归模型卡死的典型故障（`请订阅请订阅请订阅`）。

> 早期版本我写过一串具体句子（`I'm a man of few words`、`中国共产党中央委员会`、`Amara.org`…）。**那是特例处理**：换模型就漏、换语言更漏，还可能误伤真的说了这句话的音频。现在删掉了——因为"这段到底有没有人声"这个根本问题，Silero VAD 已经在上一步用模型解决了，不需要靠猜输出文本兜底。
>
> 实测验证：删掉黑名单后，同一段 79 秒录音里片头音乐**依然被丢弃**（`⨯ 丢弃 00:14–00:18（VAD 0.008）`、`⨯ 丢弃 00:19–00:20（VAD 0.003）`）——说明真正起作用的是 VAD，不是黑名单。

被丢掉的段落记为"跳过"，不进正文，也不影响时间轴。测试（`tools/test-hallucination.mjs`）也**只用构造出来的、体现约束的文本**，不绑定任何具体句子。

> 第 2 条来自 LiveTranslate 的 "speech density filter" 思路。Silero 是更根本的解法，两者叠加：Silero 拦"整段不是人声"，约束规则兜"个别句子不合物理"。两条都不需要知道说了什么内容。

## 八、参数怎么选

> 默认走实时通路，切句全自动，「每段秒数」只在回退到分段通路时才生效。

| 每段秒数（回退通路） | 适合 | 代价 |
|---|---|---|
| 10–20 秒（默认 20，首块自动 6 秒） | 想要尽快看到文字 | 请求数变多 |
| 60 秒 | 一般视频、网课 | 出字延迟约 1 分钟 |
| 300 秒 | 播客、长讲座 | 实时性差 |

接口上限：**单次 ≤ 50MB、时长 ≤ 1 小时**。16k/16bit/单声道是 32 KB/s，1 小时约 115 MB——所以超过约 26 分钟的音频必须分段，这也是默认分段的原因之一。

## 九、常见问题

**开始后视频突然没声音？** tabCapture 把声音"借走"了，插件已接回去（Web Audio 优先，`<audio>` 兜底）。若提示"音频回放被拦截"，录制仍正常，只是你听不到——或者干脆打开「静音录制」。

**有段落但文字是空的？** 那一段被 VAD 判为静音/音乐，统计里记为"跳过"。

**报 400**：该句音频太短或全静音。
**报 401 / 403**：key 错或无该模型权限。
**报 404**：接口地址或模型名不对，先用「自测接口」。
**报 429**：限流，把每段秒数调大。
**报 413**：单段太大，把每段秒数调小。

**`chrome://`、`edge://`、扩展商店页面不能录**：浏览器禁止捕获内部页面。

**提示"已经在被捕获"**：同一标签页同时只能被一个扩展捕获。

**关掉弹窗会中断吗？** 不会，录制在 offscreen 文档里跑。

**浮窗没出现？** 检查设置里「在视频页显示悬浮字幕」是否勾上（浮窗右上角 × 会关掉它）。

**点「校正全文」/「离线精校」报 `Could not establish connection. Receiving end does not exist.`？**
已修。原因是 offscreen 文档在停止录制 60 秒后会被回收，而这两个按钮是直接往 offscreen 发消息的。现在 Service Worker 会**先重建文档、再把会话状态和设置恢复进去**（`RESTORE_STATE`），然后才发命令。仿真里有专门的回归用例：关掉文档 → 点校正 → 断言"自动重建 + 恢复状态 + 校正成功"。

### 边录边切标签页、去别的网页看视频，会不会干扰？

**不会串音。** `tabCapture` 捕获的是**某一张标签页**的音频输出，绑定在标签上：你去别的标签页看视频，那个视频的声音正常从扬声器出来，**不会混进捕获流**，录制也照常继续。

但有三个真实的坑：

| 情况 | 后果 | 怎么办 |
|---|---|---|
| 被捕获的标签页自己静音、或播放器暂停 | 录到纯静音 | 面板会出现「⚠ 捕获到的音频是静音」黄条，插件也会在弹窗里提示 |
| 有些网课平台检测到"标签页不可见"会**自动暂停视频** | 同上，而且更隐蔽（视频看着在，其实停了） | 同上；发现黄条就回去点一下播放 |
| 默认会把该标签页的声音**接回扬声器** | 你切去看别的视频时，两路声音叠在一起，很难听 | 打开「静音录制」 |

所以"录着去干别的"的正确姿势：

1. 勾上 **静音录制**（否则被捕获的页面声音还在放）
2. 点「开始转录」
3. 切走干别的——**只要那张标签页还在播放**，录制和识别都不会受影响
4. 回来时看面板底部的句数就知道了

## 十二、已知限制

- **跨进度条拖动**：那一句的时间轴映射会偏（它本来就跨了不连续点）。往回拖到没识别过的地方时浮窗会显示"这一段还没识别到"。
- **没有逐字时间戳**：接口不返回字级时间，粒度是"一句"。
- **术语识别受切句影响**：已用术语表 + 校正全文兜住；根治需要热词偏置，见下一节。
- **只支持标签页捕获**：录的是"正在播放的声音"，还不能直接拖一个本地音频文件进来转（需要的话可以加，走 IndexedDB 交接给 offscreen 解码，不受 20 秒上限限制）。
- **SRT 是句级的**：时间轴来自切句结果，比早期版本准得多。
- **只录声音不录画面**。
- **DRM 内容**：声音能录到，但别用于再分发。

## 十三、要不要换成"本地部署"（WhisperLiveKit / FunASR）

先把结论说清楚：**本地部署解决的是"架构"和"热词"，不解决"模型中文能力"本身。**

### 本地方案能带来什么

| 能力 | 云端（现在） | 本地（WhisperLiveKit / FunASR） |
|---|---|---|
| 真流式（不用 VAD 硬切） | ✗ 只能按停顿切句 | ✓ 模型自己滚动解码 |
| 热词/术语偏置 | ✗ 接口忽略 prompt/hotwords（已实测） | ✓ FunASR Paraformer 有热词表；Whisper 系可用 `initial_prompt` |
| 费用 | 按调用计费 | 免费（吃自己的 CPU/GPU） |
| 隐私 | 音频上传云端 | 不出本机 |
| 说话人分离 | 换云模型（Diarize） | WhisperLiveKit 自带 |
| 安装成本 | 填个 key | Python 环境 + 1–2GB 模型 + 常驻服务 |
| 中文准确率 | Qwen3-ASR 中文很强 | 取决于模型：Paraformer/SenseVoice ≈ 同级；Whisper large-v3 中文略弱且爱编 |

### 为什么它对"术语听错"可能有用

你的错字本质是"冷启动 + 缺术语偏置"。热词表是唯一能在**识别阶段**压制它的手段，而云端接口不给这个能力（实测 4 个字段全被忽略）。WhisperLiveKit（Apache-2.0，11k star，Python/FastAPI，本地流式 + VAD + 说话人分离 + OpenAI/Deepgram 兼容 API）是现成的服务端；它的价值是"接上就能流式"，但中文术语仍要靠热词/`initial_prompt`。

### 代价（务必先想清楚）

1. 装 Python + PyTorch + 下模型，Windows 上首次跑通通常要 30–60 分钟；
2. CPU 推理比云端慢（云端 15 秒音频 0.9 秒返回，本地 CPU 可能 3–5 秒）；
3. 插件要新增一条 **WebSocket 通路**（协议要按所选服务的实现来对）、断线重连、服务发现；
4. 服务没起时插件得能优雅回退到云端。

### 建议

- **先把课上完**：术语表 + 校正全文，成本几乎为 0，已经能修掉你截图里那类错字；
- **想从根上解决术语**：优先 **FunASR Paraformer + 热词表**（中文、热词精准命中痛点）；WhisperLiveKit 更适合"多语言 + 说话人分离 + 想要 OpenAI 兼容 API"；
- 真要做，把 ASR 后端抽成可插拔接口（`cloud` / `local-ws`），加设置项切换，默认仍走云端。告诉我装哪个服务、地址端口即可。

### 现成的参考：[LiveTranslate](https://github.com/TheDeathDragon/LiveTranslate)

如果有人已经把这套东西做完了——[TheDeathDragon/LiveTranslate](https://github.com/TheDeathDragon/LiveTranslate)（Python / MIT / 837 star）就是一个：Windows 桌面程序，**抓系统音频**（WASAPI 环回，不是某个标签页），本地跑 ASR，再交给 LLM 流式翻译，浮层显示字幕。

从仓库文件看它的结构与取舍：

| 文件 | 作用 | 对本文的启发 |
|---|---|---|
| `audio_capture.py` | 系统音频 + 麦克风捕获 | **绕开了 tabCapture 的所有限制**：切标签页、全屏、静音按钮都不影响，因为它抓的是扬声器输出 |
| `vad_processor.py` | VAD 切句 | 和我们 `lib/vad.js` 同一套思路 |
| `asr_funasr.py` / `asr_funasr_nano.py` / `asr_sensevoice.py` / `asr_anime_whisper.py` | 四种 ASR 后端 | **FunASR 在列**，也就是能做中文热词 |
| `asr_server.py` + `asr_client.py` + `asr_remote.py` | ASR 拆成服务 + 客户端，支持远程 | 就是我说的"可插拔后端"该有的样子 |
| `subtitle_overlay.py` / `subtitle_window.py` | 浮层字幕 | 桌面级浮层，不局限于页面 DOM |
| `transcript_writer.py` | 落盘文稿 | 直接产出文字稿 |
| `config.yaml` | 集中配置 | 后端/模型/VAD 参数都在一处 |

**什么时候该用它、什么时候继续用这个插件**：

- 想要**完全本地 + 免费 + 热词 + 真流式**，而且不介意装个桌面程序 → LiveTranslate 更合适，它连"音频存盘"都不用你自己拼
- 只想在浏览器里点一下就用、不想装 Python 环境、想保留"页面内浮窗 + 和视频时间轴对齐" → 这个插件更顺手
- 两者可以并用：用它做高精度本地转录，用这个插件做随手录

它的短板是：Windows only、需要 Python 环境与模型下载、界面/配置是另一套；中文术语准确率仍取决于你选哪个后端模型（这点和云端一样）。

### 我从它那里逐条对照过

（下面按它的源码逐条核对，不是看 README 猜的。文件行号对应 `LiveTranslate-main/`。）

| 它的做法（源码位置） | 我们 | 说明 |
|---|---|---|
| **Silero VAD**（`vad_processor.py:124` `_silero_confidence`，512 采样/32ms 一帧） | ✅ 已实现 | `vendor/` 打包 ONNX + onnxruntime-web；真音频实测音乐段均值 0.003、讲话段 0.53 |
| **语音密度过滤**（`vad_processor.py:320` `_flush_segment`：低于阈值的帧占比 >75% 就丢整段） | ✅ 已实现 | 我们按"段平均概率 < 0.25"丢，等价且更省事（在送识别之前就丢） |
| **短段合并**（`vad_processor.py:211`：短于 min 不丢，保缓冲等下一句） | ✅ 已实现 | `targetMinMs` 2000 + 合并，碎片从 30% 降到 0 |
| **增量 ASR**（`main.py:1411` `_do_interim_asr`） | ✅ 已实现 | `lib/incremental.js` + `offscreen.js` 的 `maybeInterim`，见下 |
| **回声去重**（`main.py:1394` `_strip_committed_overlap`，取尾部 50 字对比新结果前缀） | ✅ 已实现 | `stripCommittedOverlap()`，同样 3 字以上重叠才算，避免误伤 |
| **提交后裁音频**（`main.py:1484` 比例裁剪 + 0.3 秒余量、至少留 0.5 秒） | ✅ 已实现 | `segmenter.trimFront()` + `planInterim()` 的同款比例与余量 |
| **碎片攒到下一句**（`main.py:1389` `_is_short_utterance`，≤8 字符） | ✅ 已实现 | 但阈值分语言：中日韩 3 字、拉丁 8 字符（8 个汉字已经是一句话了） |
| **渐进式静音**（`vad_processor.py:145`） | ✅ 机制已实现 | 语义是"缓冲够长才开始降阈值"，实测在我们默认 `softCut 5s` 下不会触发；想要它生效得把软上限调到 6 秒以上 |
| **自适应静音**（`vad_processor.py:82`：按最近停顿的 P75×1.2 自动调，0.3–2.0 秒） | ⬜ 没做 | 它会持续漂移，和我们"参数可预测"的目标冲突；等有真实场景需要再说 |
| **回溯切分**（`vad_processor.py:223` `_find_best_split_index`：对置信度做滑动平均找最低谷） | 🟡 部分 | 我们按**能量**找最低点；它用 Silero 置信度更准，但要把每帧概率存进切句器，收益有限 |
| **词级时间戳对齐裁剪**（`main.py:1470`，`use_word_ts` 默认关闭） | ⬜ 没做 | 它自己都默认关（太贵）。云端 ASR 也不返回词时间戳 |
| **流式翻译 + 上下文轮次**（`translator.py`） | ⬜ 不做 | 我们只做转写，不做翻译——目标不同 |
| **ASR 独立进程**（`asr_worker.py` + Pipe IPC） | ⬜ 不做 | 浏览器里没有子进程；云端识别本来就是远程调用 |

**它最核心的一招**（也是我这次真正搬过来的）：`_do_interim_asr` 不是"做个预览然后丢掉"，而是

```
对正在增长的缓冲跑识别 → 除最后一句外都已完整 → 提交出去
→ 按提交比例裁掉缓冲头部（+0.3 秒防回声）→ 记住已提交尾巴做去重
```

关键在于**切点由文本标点决定，而不是由音频能量决定**——所以它永远不会把一句话从中间切断。这正好治我实测到的病：`定稿「本部。」` 比预览的 `本部分包括以下四个内容：` 还差。

## 十四、能不能"播之前就拿到全稿"？能，看站点怎么发媒体

实时录制有个物理限制：**声音必须先播出来**。但如果页面里的媒体是直链，就没必要"录"了。

弹窗设置里的两个按钮就是干这个的：

**「探测本页媒体」** 用 `performance.getEntriesByType('resource')` **回看页面已经发出过的请求**（不用 hook、不用重放），告诉你这个站走哪条路：

| 探测结果 | 含义 |
|---|---|
`subtitle` | 页面自带 `.vtt/.srt` 字幕，直接抓（最快、质量最高） |
`hls` / `dash` | 有 m3u8/mpd 清单 → 可以下分片拼成整段音频 |
`direct` | `<video>` 是直链 mp4/mp3 → 可以整段下载 |
`mse` | `blob:` + MSE，没有稳定链接 → 只能实时录 |

**「整段提取（不用等播放）」** 对 `direct` 的站直接可用：下载 → 浏览器 `decodeAudioData` 解码 → 16k 单声道 → 20 秒窗口切句 → 整段转写 → 自动纠错。时间轴天然对齐文件开头，比录制推算更准。

实测：学堂在线（雨课堂）一节 **8 分 49 秒** 的课，直链 36.8 MB，**26 秒**转完 80 句 / 1829 字。

限制：单文件 ≤ 600 MB、时长 ≤ 45 分钟（`decodeAudioData` 要整段进内存）；DRM（Widevine）加密的无解。

## 十五、数据存在哪？会丢吗？

| 东西 | 存在哪 | 关浏览器 | 重开新会话 | 清空 |
|---|---|---|---|---|
文字稿 | `chrome.storage.local`（浏览器 profile） | **不丢** | 进历史（最多 5 份） | 进历史 |
音频（勾了"同时保存音频"才有） | OPFS（同源文件系统） | **不丢** | 保留 | **删除** |
导出的 SRT/TXT | 你自己选的磁盘位置 | 不丢 | 不丢 | 不丢 |

所以：

- **要长期保存，一定要点「导出 SRT」**——不导出的话数据只在浏览器里（虽然关浏览器不丢，但清浏览器数据/换 profile 就没了）
- 「重新开始」和「清空」都**不会真的删掉稿子**，会先存进历史；弹窗里会出现 **「恢复上一份（N）」** 按钮，点一下就能找回并重新导出
- 音频是例外：清空会删 OPFS 里的 WAV（体积大，不保留多份）
- 整段提取的音频**不写 OPFS**（直接内存里解码），所以那条路没有「保存音频」和「离线精校」；要用就重新提取，或改用录制

## 十六、字幕库（按视频保存）

跑完「整段提取」的稿子会**自动按视频存起来**，下次打开同一个视频不用再识别、也不用重新下载。

### 键怎么算

```
归一化 URL（丢掉 auth_key / sign / utm_* 这类会变的签名参数，
          保留 bvid / vid / cid / chapter 这类真标识）
+ 视频时长（取整到秒，同一页换集也能分清）
```

纯逻辑在 `lib/videokey.js`，测试见 `tools/test-videokey.mjs`。

### 存哪、为什么不用 IndexedDB

放 `chrome.storage.local` 的 `asrDocs` 字段下。原因：内容脚本（面板）跑在**页面**的源上，
它的 IndexedDB 属于那个网站，不是扩展的；只有 SW / offscreen / popup 共享扩展源。
字幕库要"任意页面都能读到"，所以走 chrome.storage 最省事。
容量也够：一份稿子 6–12KB，本地配额 10MB，几百份没问题；超过 80 份淘汰最旧的。

### 行为

| 场景 | 行为 |
|---|---|
整段提取完成 | 自动入库（`DOC_SAVE`） |
打开同一个视频 | 面板发现当前稿子不属于本页 → 自动向字幕库取（`DOC_LOAD`），命中就直接显示 |
打开没存过的视频 | 一行都不显示，提示"本页还没有对应的文字稿"（绝不显示别的视频的） |
弹窗底部 | 「字幕库」下拉 + 加载 / 删除 |

## 十七、设置页怎么分组

弹窗分**两个标签页**（不是往下展开的折叠块）：

**「转录」**（默认，日常用）
- 标签页 / 播放状态
- 计时 + 开始/停止 + 进度
- 整段提取、探测本页媒体、整段预扫
- 文字稿（复制/导出/校正/精校/显示到页面/恢复上一份/清空）
- 字幕库下拉 + 加载 / 删除

**「设置」**（改一次就不动）
- 顶部**吸顶操作条**：保存设置 / 自测接口 / VAD 自检（改完就在眼前，不用滚到底）
- 接口：API Key、模型名、接口地址、纠错模型
- 显示：悬浮字幕开关、字号
- 音频：静音录制、保存音频
- 识别：Silero VAD、增量提交、每段秒数、预扫倍速
- 术语表

分组判据：**"每次都要点"的放转录页，"改一次就不动"的放设置页**；
设置页的操作按钮必须**吸顶**，因为它的使用路径永远是"改 → 立刻保存"。
